# LOKF findings, for the LinkML developer call on 2026-09-02

Mark Miller (LBNL), for Nolan Nichols and the LinkML developers.

At the 2026-08-12 dev call, Nolan's LOKF work was raised, Nolan said he would be honoured to have
it picked up by the LinkML org, and I said I would look at it and report back. This is that
report. It is not a recommendation for or against adoption. It is what two days of building with
LOKF showed about its strengths, its weaknesses, and which direction the benefit runs between it
and LinkML.

Everything below was measured against `lokf` 0.5.0 and, where a LinkML version matters,
`linkml` 1.11.1. The bundle is public: https://github.com/turbomam/nmdc-lokf-demo, published at
https://turbomam.github.io/nmdc-lokf-demo/.

**What this does not show.** No retrieval comparison was run. Nothing here measures whether LOKF
improves search, curation or reuse. The subject is what the conversion costs and what the
toolchain does, not what it buys.

## What LOKF is, in one paragraph

Markdown with YAML frontmatter, converted to JSON-LD and then RDF by a Python toolkit. The format
is defined by one hand-edited LinkML schema, `lokf.yaml`, 1,624 lines. That schema generates the
JSON-LD context, JSON Schema, SHACL shapes, an OWL ontology, SQL DDL and Python bindings. The
wheel ships `lokf.yaml`, the context and the bindings; the other four stay upstream, and
`lokf validate` reaches the JSON Schema by running `linkml-validate` against the packaged
`lokf.yaml` rather than by shipping a generated schema.

A `lokf new` scaffold also writes an Astro site. That half is optional: the Python package
declares no Node dependency, and deleting every scaffolded file costs only the published website.

## The finding most relevant to LinkML itself

Exercising the profile surfaced a LinkML behaviour, not a LOKF one. **`linkml-validate` returns
different verdicts for the same data depending on the serialisation it is loaded from.**

```
$ linkml-validate -s s.yaml -C T <each file>          # linkml 1.11.1

  empty.yaml   tags: []          No issues found
  empty.json   {"tags": []}      [ERROR] 'tags' is a required property in /
  null.yaml    tags: null        [ERROR] None is not of type 'array' in /tags
  null.json    {"tags": null}    [ERROR] 'tags' is a required property in /
```

One schema, one slot that is `multivalued` and `required`, two values, each written both ways. As
YAML the empty list validates clean; as JSON it is reported missing.

The mechanism: LinkML's JSON loader runs `json_clean`, which strips empty collections and nulls,
while the YAML loader passes `yaml.safe_load_all` output through unchanged. The ordinary presence
check then fires on a document that no longer contains the key. The two JSON rows matter because
they *agree*: two distinct inputs collapsing onto one verdict, word for word the verdict an absent
key produces, is what identifies a normalisation step rather than a stricter rule.

This reaches LOKF authors without their ever writing JSON, because `lokf validate` writes a
temporary `.bundle.json` and validates that.

The exposure is any slot that is `multivalued`, `required` and legitimately empty. That is not
exotic: it is the shape of every "list of things, sometimes none" field.

Reproduction, four files and a schema:
https://github.com/turbomam/nmdc-lokf-demo/tree/main/docs/examples/loader-normalization

**Already filed upstream.** https://github.com/linkml/linkml/issues/3440, open since 2026-04-23,
describes the same mechanism: `JSONLoader` runs `Loader.json_clean` on every load, deleting any
key whose value is `None`, `[]` or `{}`, while `YAMLLoader` does not. It names the validator-side
loaders too, so `linkml-validate` inherits the asymmetry. We hit it independently and the
reproduction above is a second, minimal case. Whether it is a bug, a documented loader difference,
or intended, is still the question for this call.

## What the conversion actually cost

The bundle re-expresses six findings from an existing prose knowledge base as concepts: four
datasets, one glossary term, one explanation.

**The frontmatter mapping is the work; the syntax is not.** The source bundle used
`name` / `description` / `metadata` / `related`. LOKF wants typed relations. So adopting it was a
modelling exercise, not a relabelling, and the interesting part was where one source field had to
become two:

- `metadata.provenance` split into a producer tag and a `derivedFrom` link, because it had been
  carrying both "who made this" and "what it came from".
- `metadata.tenant` became a `dependsOn` link, because where a thing is hosted is not who
  produced it.

That split is the whole value of the exercise and it is not something the tooling can do for you.
Six concepts produced 9 edges and exactly one `prov:wasDerivedFrom`, which is itself informative:
the prose had implied a great deal more derivation than the data supported.

**What LOKF adds over plain OKF** is that the fields bind to established vocabularies:
`derivedFrom` becomes `prov:wasDerivedFrom`, `dependsOn` becomes `dcterms:requires`. That is the
part worth having, and it is the part that comes from the LinkML schema.

## Four defects in a default install, all filed

None of these are deep, and all were hit inside a day of first use:

- `lokf validate` fails in a default install, because `linkml-validate` is not on `PATH`.
  https://github.com/nicholsn/lokf/issues/33
- Scaffolded agent skills reference `examples/acme-knowledge`, which `lokf new` does not create.
  https://github.com/nicholsn/lokf/issues/34
- The scaffolded site distinguishes prose links by colour alone, with footer links at 1.00:1
  against the surrounding text.
  https://github.com/nicholsn/lokf/issues/35
- The README's manual `base_iri` step names two of the four places that hold it.
  https://github.com/nicholsn/lokf/issues/36

All four were open and untriaged as of 2026-08-27, one day after filing, which is far too short an
interval to mean anything.

**A fifth, not filed, which bears on the org question directly.** The scaffold writes the
bundle's `@context` as

```
https://raw.githubusercontent.com/nicholsn/lokf/main/lokf.context.jsonld
```

A moving branch, in one person's repository, served as `text/plain`. Every term in a published
LOKF graph means whatever that file contains at the moment a consumer resolves it, so an upstream
edit changes the semantics of every deployed bundle with no commit anywhere downstream. This is
the scaffold default, so every LOKF bundle inherits it.

That is not a criticism of a young project; it is exactly the kind of thing an org adoption would
fix, since a stable versioned context IRI is infrastructure rather than code.

## Strengths

**The format is thin enough to hold in your head.** One hand-edited LinkML schema, 1,624 lines, a
small vocabulary, and bindings to schema.org, DCAT and PROV-O that are conventional rather than
invented. Nothing about the modelling looked wrong, and a reader can learn the whole thing in an
afternoon.

**Markdown with frontmatter is a good authoring surface.** Concepts stay readable and diffable as
prose, and become RDF without a second file to keep in sync. That is the property people actually
want from this class of tool, and LOKF delivers it.

**The typed relations do real work.** `derivedFrom` becoming `prov:wasDerivedFrom` and `dependsOn`
becoming `dcterms:requires` is the difference between a document set and a graph. Six concepts
produced 9 edges and a SPARQL query that separates producers from hosts, which prose in the same
repository had been conflating.

**The Python core has no Node dependency.** `lokf convert`, `validate`, `query`, `serve`, `tables`
all work without the scaffolded website, and `lokf serve` gives a SPARQL endpoint and a graph
explorer from stdlib `http.server` and pyoxigraph. The Astro site is optional scaffolding, and
deleting it costs only the published pages.

## Weaknesses

**The first-run path is where the defects are.** Four in a day of ordinary use, all filed:

- `lokf validate` fails in a default install, because `linkml-validate` is not on `PATH`.
  https://github.com/nicholsn/lokf/issues/33
- Scaffolded agent skills reference `examples/acme-knowledge`, which `lokf new` does not create.
  https://github.com/nicholsn/lokf/issues/34
- The scaffolded site distinguishes prose links by colour alone, with footer links at 1.00:1
  against the surrounding text.
  https://github.com/nicholsn/lokf/issues/35
- The README's manual `base_iri` step names two of the four places that hold it.
  https://github.com/nicholsn/lokf/issues/36

All four were open and untriaged as of 2026-08-27, one day after filing, which is far too short an
interval to mean anything.

**The published context is not pinned.** The scaffold writes the bundle's `@context` as

```
https://raw.githubusercontent.com/nicholsn/lokf/main/lokf.context.jsonld
```

A moving branch, in one person's repository, served as `text/plain`. Every term in a published
LOKF graph means whatever that file contains when a consumer resolves it, so an upstream edit
changes the semantics of every deployed bundle with no commit downstream. This is the scaffold
default, so every LOKF bundle inherits it.

**The mapping is the work, and the tooling cannot help with it.** Converting an existing prose
bundle meant splitting `metadata.provenance` into a producer tag and a `derivedFrom` link, because
it had been carrying both "who made this" and "what it came from", and turning `metadata.tenant`
into `dependsOn`. That is a modelling conversation, not a relabelling, and it is the real cost of
adoption.

**Dereferencing gives less than the format implies.** A concept IRI resolves to HTML carrying a
schema.org stub of `name` and, if present, `description`. The typed relations exist only in the
whole-graph document. A glossary term resolves to a bare name, because its `definition` is not
mapped. Reasonable for a static site, but worth knowing before promising anyone dereferenceable
linked data.

## Which direction the benefit runs

**What LOKF gets from LinkML: nearly everything structural.** One schema generates the JSON-LD
context, JSON Schema, SHACL, OWL, SQL DDL and Python bindings. 1,624 lines in, 16,648 out. Without
LinkML, LOKF is a markdown convention with a hand-maintained context file; with it, the vocabulary
bindings, the validation and the language bindings all fall out of one definition. This is close to
the strongest small demonstration of the LinkML value proposition I have built.

**What LinkML gets from LOKF: a test surface, and it already paid.** Exercising a real
LinkML-defined format against real data surfaced a LinkML behaviour that neither the schema nor the
data would show alone: `linkml-validate` returns different verdicts for the same instance depending
on the serialisation it is loaded from. That finding is in the section above and reproduces from
four committed files. A profile people actually build with exercises paths the compliance suite
does not, and that is worth something to LinkML independent of LOKF's own merits.

**There is a third direction, and it is the one the org question actually turns on: what LOKF
offers LinkML's users.** That is not the same as what it offers LinkML the project, and it is
larger. It is the Strengths section above: markdown with frontmatter that becomes RDF without a
second file to keep in sync, typed relations that turned six concepts into nine edges and a SPARQL
query separating producers from hosts where the prose had conflated them, and a Python core that
works with no Node dependency. Someone deciding whether LinkML should adopt LOKF is really asking
whether LinkML's users would be better off with it in the org, and that is the evidence for it.

**The asymmetry is worth stating plainly.** LOKF depends on LinkML for its structure. LinkML the
project does not depend on LOKF for anything, but gains a realistic downstream user, which is a
different and smaller kind of benefit. Those are three separate things and anyone weighing closer
association should weigh them separately rather than netting them.

## What would make the next round of this better

Nothing here measures retrieval or curation, and that is the question anyone deciding to adopt
this will actually ask. The next step is a fixed-query baseline against an already-ingested corpus
before anything is indexed differently, so that a comparison exists rather than an impression.
